## 4. Maintenance Windows — обязательные возможности

Необходимо реализовать плановые окна обслуживания.

### 4.1. Создание окна

Пользователь должен иметь возможность создать окно обслуживания для:

- Отдельного монитора.
- Группы мониторов.

У каждого окна:

- UUID.
- Название или описание.
- Target type.
- Target ID.
- Время начала.
- Время окончания.
- Время создания.
- При необходимости — версия конфигурации.

### 4.2. Валидация

Проверь:

- Время окончания позже времени начала.
- Корректный часовой пояс.
- Существование monitor/group.
- Невозможность указать одновременно monitor и group в одном окне.
- Невозможность создать окно без целевого объекта.
- Корректную обработку пересекающихся окон.
- Корректную обработку удаления связанного монитора или группы.

Используй UTC в PostgreSQL.

Для интервалов установи правило:

`start_at <= current_time < end_at`

Начальная граница включается, конечная исключается.

Точное поведение границ должно покрываться автоматическими тестами.

### 4.3. Поведение мониторинга

**Maintenance не должен останавливать HTTP-проверки.**

Во время обслуживания:

- Worker продолжает работу.
- HTTP-запросы продолжают выполняться.
- CheckResult сохраняются.
- Incident Lifecycle продолжает работать.
- Реальное состояние UP/DOWN сохраняется.
- Dashboard показывает фактическое состояние.
- Дополнительно отображается признак MAINTENANCE.
- Запрещена отправка подавляемых email-уведомлений.

Нельзя подменять DOWN на UP во время обслуживания.

### 4.4. Группы и пересечения

Один монитор может входить в несколько групп.

Разработай правильную модель применимости maintenance:

- Окно монитора подавляет уведомления этого монитора во всех группах.
- Окно группы подавляет уведомления соответствующим получателям этой группы.
- Окно одной группы не должно необоснованно блокировать другую независимую группу.
- Пересекающиеся окна продолжают подавление, пока остаётся хотя бы одно применимое активное окно.

Необходимо документировать правила.

### 4.5. Завершение обслуживания

Если окно завершилось, но сайт продолжает находиться в DOWN:

- Система должна определить наличие неуведомлённого активного инцидента.
- Создать необходимое логическое уведомление DOWN.
- Поставить его в очередь отправки.
- Не создавать второй инцидент.
- Не отправлять повторные уведомления при каждом следующем цикле worker.

**Важный случай:** окончание maintenance должно обрабатываться независимо от поступления следующего HTTP CheckResult.

Предусмотри отдельную периодическую reconciliation-процедуру.

Если сайт восстановился до завершения maintenance и DOWN не был отправлен:

- Не отправлять устаревшее DOWN.
- Не отправлять бессмысленное RECOVERY для уведомления, которого получатель не видел.

## 5. Transactional Outbox — архитектура

Создай полноценную подсистему надёжной асинхронной доставки.

Используй PostgreSQL как источник истины.

Не добавляй Redis, RabbitMQ или Kafka без доказанной необходимости.

### 5.1. Отдельная таблица Outbox

Создай миграцию:

`0004_maintenance_outbox.py`

Миграция должна быть аддитивной.

Предлагаемые поля Outbox:

- id.
- incident_id.
- group_id.
- event_type.
- recipient или зафиксированный recipient payload.
- status.
- attempts.
- created_at.
- next_attempt_at.
- claimed_at или lease_until.
- lease_token.
- sent_at.
- last_error.
- idempotency_key.

Допускается нормализованная модель NotificationEvent + NotificationDelivery, если это упрощает корректную дедупликацию по получателям.

Обязательно обоснуй выбранную структуру.

### 5.2. Типы событий

Предусмотри:

- DOWN.
- RECOVERY.

Административные причины:

- PAUSED.
- CONFIG_CHANGED.

не должны автоматически считаться успешным восстановлением.

Если нужны дополнительные внутренние состояния, используй их только по обоснованной необходимости.

### 5.3. Атомарность

При подтверждённом переходе в DOWN:

1. HTTP-наблюдение сохраняется.
2. Состояние монитора обновляется.
3. Инцидент создаётся.
4. Необходимое событие уведомления фиксируется в той же транзакции.

Нельзя сначала записать инцидент, затем завершить транзакцию и только потом без защиты создать событие.

При ошибке транзакции изменения должны откатываться согласованно.

При восстановлении событие RECOVERY должно быть согласовано с закрытием исходного инцидента.

**SMTP-отправка не должна выполняться внутри транзакции сохранения HTTP-наблюдения.**

## 6. Дедупликация уведомлений

Это один из самых важных критериев этапа.

### 6.1. Однократность логических событий

Для одного инцидента нельзя бесконечно создавать DOWN-события.

Для одного подтверждённого восстановления нельзя создавать повторные RECOVERY-события.

Применяй уникальные ключи и ограничения PostgreSQL.

Не ограничивайся проверкой в памяти Python.

### 6.2. Получатели нескольких групп

Один и тот же email может присутствовать в нескольких группах, связанных с одним монитором.

Определи и реализуй явную политику, предотвращающую необоснованные повторные письма одному адресу об одном событии.

Необходимо учитывать:

- Один монитор в нескольких группах.
- Один адрес в нескольких группах.
- Разные maintenance windows этих групп.
- Разные сроки допустимой отправки.
- Изменения списка получателей во время открытого инцидента.

Раздели понятия:

- Логическое событие.
- Групповой маршрут уведомления.
- Фактическая доставка конкретному получателю.

Не упрощай эти случаи ценой нарушения maintenance.

### 6.3. Замороженные получатели

Для события, готового к отправке, должна сохраняться определённая версия списка получателей.

Выбери и задокументируй момент фиксации получателей.

Если настройки группы меняются во время отложенного уведомления, корректно обработай исключённых и новых получателей согласно выбранной политике.

Не отправляй письма неизвестным адресатам.

## 7. Порядок DOWN и RECOVERY

Обязательно реализуй предсказуемое поведение.

### Сценарий A

Сайт падает → DOWN отправлен → сайт восстанавливается.

Результат:

- Одно логическое DOWN.
- Одно логическое RECOVERY.
- Правильный порядок.

### Сценарий B

Сайт падает → DOWN находится в очереди → сайт быстро восстанавливается.

Реши и документируй политику для ещё не отправленного DOWN.

Не допускай бессмысленного порядка RECOVERY → DOWN.

### Сценарий C

DOWN отправлен → началось maintenance → сайт восстановился внутри окна.

Учитывай, что ранее DOWN уже был принят SMTP.

Не теряй необходимое уведомление о восстановлении.

При этом соблюдай правила подавления email во время maintenance.

### Сценарий D

Сайт падает во время maintenance → восстанавливается до окончания окна.

Не отправляй пару устаревших писем.

### Сценарий E

Сайт падает во время maintenance → окно заканчивается → сайт остаётся DOWN.

Отправь DOWN один раз.

### Сценарий F

Во время инцидента пользователь нажал Pause или изменил конфигурацию.

Не отправляй ложное RECOVERY.

Учитывай состояние ранее отправленных уведомлений.

Необходимо явно описать выбранное поведение административных закрытий.

## 8. SMTP и Mailpit

В проекте уже есть Mailpit.

Используй его для реальной локальной проверки отправки email.

Не требуется подключать Gmail, SendGrid или платные email-провайдеры.

### 8.1. Отправка

Реализуй отдельный dispatcher.

Он должен:

1. Находить готовые события.
2. Атомарно резервировать отправку.
3. Выполнять SMTP-операцию вне длительной транзакции PostgreSQL.
4. Сохранять результат.
5. Обрабатывать ошибки.
6. Назначать повторную попытку.
7. Предотвращать параллельное взятие одной задачи несколькими dispatchers.

### 8.2. Повторные попытки

Используй ограниченный exponential backoff.

Предусмотри:

- SMTP unavailable.
- Connection refused.
- Timeout.
- Temporary SMTP error.
- Permanent SMTP error.
- Worker cancellation.
- Restart before sending.
- Restart after SMTP acceptance but before database acknowledgement.

Определи правила для временных и постоянных ошибок.

Не допускай бесконечного агрессивного повторения.

Не создавай неограниченно растущие логи ошибок.

### 8.3. Честная гарантия доставки

Не заявляй абсолютную exactly-once delivery.

Если SMTP принял письмо, но приложение аварийно завершилось до сохранения sent_at, физическое повторение возможно.

Документируй различие между:

- Exactly-once logical event creation.
- Idempotent database scheduling.
- At-least-once delivery attempts.
- SMTP acceptance.
- Actual delivery в почтовый ящик.

Проверяй гарантии, которые действительно обеспечивает выбранная реализация.

## 9. Конкурентная работа dispatcher

Используй PostgreSQL-транзакции, подходящие блокировки и leases.

Проверь:

1. Два dispatcher одновременно пытаются отправить одно событие.
2. Один dispatcher падает после claim.
3. Lease истекает.
4. Старый dispatcher возвращается после истечения lease.
5. Отправка завершилась ошибкой.
6. Состояние инцидента изменилось во время ожидания.
7. Maintenance начался, пока событие ожидало отправки.
8. Maintenance завершился во время попытки.
9. Список получателей изменился.
10. Удалена группа или монитор.

Перед фактическим SMTP-send необходима повторная проверка допустимости отправки.

Учитывай, что одно чтение состояния до сетевого вызова не исключает всех гонок. Проанализируй граничный случай начала maintenance одновременно с отправкой письма и документируй фактическую гарантию синхронизации.

Нельзя держать PostgreSQL-транзакцию открытой на всё время сетевого SMTP-запроса без сильного технического обоснования.

- Корректно продолжать работу после рестарта.

Предусмотри адекватный интервал polling.

Не создавай бесконечные циклы без задержек.

Не дописывай несуществующие HTTP CheckResult ради запуска reconciliation.

Во время внедрения outbox в базе могут находиться старые открытые инциденты, созданные до появления системы email.

Разработай честную политику миграции.

Не выполняй автоматическую массовую отправку писем по старым инцидентам без явного решения.

Не создавай фиктивные исторические email-события.

Документируй начальное состояние и дальнейшее поведение.

## 14. Полный набор автоматических тестов

### Maintenance

Проверь:

- CRUD.
- Корректность дат.
- Границы start/end.
- Пересечение окон.
- Окно отдельного монитора.
- Окно группы.
- Несколько групп.
- Смена состава группы.
- Удаление целевого объекта.
- Перезапуск сервера.
- Сохранение реального мониторинга во время обслуживания.

### Outbox

Проверь:

- Создание DOWN-события.
- Создание RECOVERY-события.
- Atomic rollback.
- Unique constraints.
- Повторные ошибки мониторинга.
- Дедупликацию получателей.
- Два dispatcher.
- Истечение lease.
- Ошибки SMTP.
- Retry/backoff.
- Отложенную отправку.
- Отмену устаревшего DOWN.
- Правильный порядок событий.
- Поведение после рестарта.

### Mailpit Integration

Выполни настоящий сценарий:

1. Создай тестовую группу.
2. Добавь тестовый email.
3. Добавь монитор.
4. Симулятор отвечает 200.
5. Переведи симулятор в 500.
6. Дождись достижения порога.
7. Проверь появление DOWN в Mailpit.
8. Продолжи неуспешные проверки.
9. Проверь отсутствие новых повторных писем.
10. Верни симулятор в 200.
11. Проверь RECOVERY.
12. Убедись, что письма соответствуют одному инциденту.

Затем повтори этот сценарий внутри maintenance window.

Во время активного окна Mailpit не должен получать подавленные письма.

После окончания окна при продолжающемся DOWN должно появиться необходимое уведомление.

Используй реальный Mailpit API для проверки фактически принятых сообщений.

Не ограничивайся моками SMTP.

### Browser E2E

Проверь:

- Создание окна обслуживания.
- Редактирование окна.
- Удаление окна.
- Видимость maintenance.
- Две вкладки.
- SSE reconnect.
- Изменения статусов.
- Настройки email-получателей.

### Regression

Повторно выполни все ранее созданные тесты этапов 1–3.

Проверки:

- Backend.
- Frontend.
- Playwright.
- TypeScript.
- Lint.
- Format.
- Build.
- Migration.
- Docker.
- HTTP smoke.
- GitHub Actions после публикации.

Нельзя удалить старые тесты ради успешной проверки нового функционала.

## 18. Критерии завершения

Этап 4 считается завершённым только если:

1. Реализован Maintenance CRUD.
2. Окна работают для мониторов.
3. Окна работают для групп.
4. Пересекающиеся окна обрабатываются правильно.
5. HTTP-проверки продолжаются во время обслуживания.
6. Реальное состояние DOWN сохраняется.
7. Email подавляется при активном применимом maintenance.
8. После завершения окна DOWN уведомляется, если проблема сохраняется.
9. При восстановлении до окончания окна нет ложной пары писем.
10. Outbox хранится в PostgreSQL.
11. События создаются атомарно с соответствующими переходами Incident Lifecycle.
12. Нет повторных логических DOWN/RECOVERY.
13. Повторная SMTP-отправка управляется persisted retry.
14. Несколько dispatcher не обрабатывают одну задачу как разные независимые события.
15. После рестарта очередь восстанавливается.
16. Реальная доставка в Mailpit проверена.
17. UI позволяет управлять maintenance.
18. Две вкладки обновляются автоматически.
19. Все предыдущие тесты продолжают проходить.
20. Новые тесты выполнены.
21. Миграция сохраняет старые данные.
22. Документация соответствует фактическому результату.
23. Все реальные коммиты и timestamps сохранены.
24. PR подготовлен.
25. Нет необъяснённых BLOCKER/HIGH дефектов.

Если есть ограничения, отметь их честно.
