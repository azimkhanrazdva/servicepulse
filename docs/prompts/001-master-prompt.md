3. Оригинальное тестовое задание Mad Devs

Должно быть реализовано:

* Приостановка проверки.
* Возобновление проверки.

B. Группы

* Общий статус каждой группы.
* Индивидуальные настройки email-уведомлений для каждой группы.

C. Dashboard

* Текущий статус.
* HTTP-код ответа.
* Время ответа.
* Время последней проверки.

* Процент доступности за неделю.
* Процент доступности за месяц.
* Журнал инцидентов.
* Время начала инцидента.
* Время восстановления.
* Продолжительность инцидента.

E. Maintenance Windows

* Плановое окно обслуживания для проверки.
* Плановое окно обслуживания для группы.
* Во время обслуживания проверки продолжаются.
* Мониторинг и статус продолжают работать.
* Оповещения во время обслуживания подавляются.
* Если обслуживание закончилось, а сайт всё ещё недоступен, нужно отправить необходимое уведомление.

* Корректное поведение при сбоях отправки почты.

G. Публичная статусная страница

* Доступная по ссылке страница состояния сервисов.
* Без обязательной авторизации.
* Автоматическое обновление информации.
* Отображение только тех данных, которые владелец разрешил опубликовать.

3.3. Обязательные сценарии поведения

Реализуй и проверь следующее:

1. Статусы на dashboard меняются автоматически без перезагрузки.
2. Публичная статусная страница также обновляется автоматически.
3. При падении сайта отправляется письмо.
4. После восстановления приходит второе письмо.
5. Между этими событиями не отправляются повторные письма, сколько бы проверок ни завершилось ошибкой.
6. Единичная кратковременная ошибка не считается подтверждённым падением.
7. Инцидент открывается после прохождения выбранного порога ошибок.
8. При восстановлении инцидент автоматически закрывается.
9. В окне обслуживания проверки не останавливаются.
10. Во время обслуживания письма подавляются.
11. После окончания обслуживания всё ещё неработающий сайт вызывает уведомление.
12. Проверка, выполнение которой превышает интервал, не запускается второй раз параллельно самой себе.
13. 50 проверок с интервалом 30 секунд не блокируют друг друга.
14. Один медленный сайт не задерживает остальные.
15. Месячная история открывается быстро.
16. Публичная страница не раскрывает скрытые данные.
17. После перезапуска backend/worker проверки продолжаются с прежними настройками.
18. Период простоя сервера обозначается отсутствием наблюдений, а не падением сайта.

Каждое обязательное требование должно получить уникальный ID, критерии приёмки и проверяемое подтверждение.

5. Архитектура бизнес-логики

Отнесись к этому разделу особенно внимательно.

5.1. Состояния проверок

Предложи понятную модель:

* UNKNOWN.
* UP.
* DOWN.
* PAUSED.

При необходимости можно добавить DEGRADED или иные внутренние состояния, но не усложняй систему искусственно.

Определи:

* Что происходит при первом успешном запросе.
* Что происходит при первой ошибке.
* Когда именно открывается инцидент.
* Когда он закрывается.
* Что происходит при ручной проверке.
* Как ведёт себя PAUSED.
* Как определяется статус группы.
* Как статус отображается во время maintenance.

Базовый порог: две последовательные ошибки для подтверждения падения. Обоснуй выбор и сделай его настраиваемым, если это не создаёт ненужную сложность.

Все правила должны быть явно описаны и протестированы.

5.2. Асинхронные проверки

Нельзя выполнять HTTP-проверки так, чтобы один медленный ресурс блокировал остальные.

Используй:

* Асинхронные запросы.
* Ограничение конкурентности.
* Таймауты.
* Пул HTTP-соединений.
* Корректную отмену задач.
* Обработку сетевых ошибок.
* Исключение пересекающихся запусков одного monitor.

Рассмотри конкурентные изменения конфигурации во время выполнения проверки.

5.3. Уведомления

Обеспечь идемпотентность логических событий.

Для каждого инцидента необходимо предотвращать повторное создание одинаковых уведомлений.

Рекомендуется transactional outbox с уникальными ключами событий.

Разделяй:

* Создание события уведомления.
* Сохранение события.
* Попытку отправки.
* Подтверждение отправки.
* Повторную попытку после ошибки.

Не заявляй абсолютную гарантию exactly-once email delivery, если используемый SMTP-сервис её не обеспечивает.

Для тестового задания необходимо обеспечить и доказать отсутствие дублирующихся логических уведомлений.

5.4. Maintenance windows

Разделяй состояние сервиса и политику уведомления.

Окно обслуживания не означает, что проверка считается успешной.

Реальное состояние должно продолжать записываться, но email-политика должна учитывать активное окно обслуживания.

Корректно обработай:

* Maintenance для одной проверки.
* Maintenance для группы.
* Пересекающиеся окна.
* Начало и окончание окна.
* Восстановление до конца окна.
* Сайт остаётся DOWN после конца окна.

5.5. Перезапуски

После рестарта:

* Сохраняются настройки мониторов.
* Сохраняются группы.
* Сохраняются результаты.
* Сохраняются инциденты.
* Возобновляются запланированные проверки.
* Не создаются вымышленные результаты за период простоя.
* Не возникают ложные инциденты только из-за рестарта.
* Не происходит массовое дублирование писем.

5.6. Производительность

Подготовь тест на 50 независимых проверок с интервалом 30 секунд.

Используй локальный симулятор сайтов, чтобы нагрузочные проверки были воспроизводимыми.

Измеряй:

* Количество успешных запусков.
* Фактическую частоту выполнения.
* Максимальную конкурентность.
* Количество пропущенных или задержанных проверок.
* Влияние медленных ресурсов.
* Отсутствие пересекающихся запусков.
* Время получения месячной истории.

Не придумывай результаты производительности. Указывай реальные измерения, параметры окружения и ограничения эксперимента.

6. Безопасность

Даже тестовое приложение должно иметь разумную базовую безопасность.

Особенно важно защитить backend, выполняющий HTTP-запросы по URL пользователя.

Проанализируй риски SSRF.

Предусмотри:

* Валидацию URL.
* Допустимые схемы HTTP/HTTPS.
* Защиту от запросов к запрещённым адресам.
* Контроль перенаправлений.
* Безопасную обработку DNS и изменения адресов, насколько это позволяет выбранная реализация.
* Контроль таймаутов и размера HTTP-ответов.
* Ограничение раскрытия внутренних ошибок через API.
* Отсутствие секретов в Git.
* Отсутствие внутренней информации на публичных статусных страницах.

Так как локальный симулятор должен быть доступен для проверок, предусмотрим отдельную явно включаемую настройку для тестовой среды. Не ослабляй ограничения по умолчанию для произвольных внешних URL.

Если есть неизбежные ограничения безопасности для проекта без авторизации и публично доступного интерфейса, документируй их.

8. Симулятор тестовых сайтов

Создай отдельный сервис, который позволяет эмулировать:

* HTTP 200.
* HTTP 404.
* HTTP 500.
* Задержанный ответ.
* Превышение таймаута.
* Отсутствие ответа или сбой соединения, насколько это возможно эмулировать.
* Неожиданный HTTP-код.
* Ожидаемую/неожидаемую строку в ответе.
* Переход из UP в DOWN.
* Переход из DOWN в UP.

11. Git, Commits и Pull Requests

Настрой Git-репозиторий, если он отсутствует.

Используй профессиональный подход GitHub Flow.

Commit rules

* Коммиты после завершённых логических изменений.
* Короткие содержательные сообщения.
* Conventional Commits.
* Никаких бессмысленных update, fix stuff, changes.
* Никаких сфальсифицированных дат.
* Никакого backdating.
* Никаких секретов.
* Никаких принудительных изменений уже опубликованной истории.
* Никаких непроверенных массовых коммитов.

Примеры сообщений:

* chore: initialize full-stack project
* feat(api): implement monitor management
* feat(worker): add concurrent monitoring scheduler
* feat(incidents): implement incident lifecycle
* feat(notifications): add idempotent alert outbox
* feat(ui): add realtime monitoring dashboard
* test: add concurrency and recovery coverage
* docs: finalize deployment and development evidence

Branch strategy

Используй feature branches для значительных логических изменений.

Предпочтительные PR:

1. Project foundation.
2. Monitoring backend.
3. Scheduler and notifications.
4. Frontend and realtime.
5. Integration, reliability and documentation.

Это ориентир, не обязательное число PR.

Не создавай пустые PR ради демонстрации активности.

Git workflow

Для каждой фазы:

1. Создай подходящую ветку.
2. Внеси изменения.
3. Выполни соответствующие проверки.
4. Проанализируй git diff.
5. Проверь отсутствие секретов.
6. Обнови журнал разработки.
7. Сделай логические локальные коммиты с настоящим временем.
8. Подготовь PR summary.
9. Если удалённый репозиторий настроен, запроси моё подтверждение для push/PR.
10. После проверки и разрешения выполни публикацию и merge.

Если GitHub CLI отсутствует или не авторизован, не проси мои пароли и токены в чат.

Сообщи, что именно требуется подключить.

Не заявляй о создании GitHub PR, если он фактически не создан.
