# ЧАСТЬ II — FAULT TESTING ПОД НАГРУЗКОЙ

## 6. ДОПОЛНИТЕЛЬНЫЙ НАГРУЗОЧНЫЙ ТЕСТ

Предыдущий тест 50 × 30 секунд успешно выполнен.

Не повторяй его просто ради повторения.

Теперь проведи дополнительные испытания при работающих мониторах.

### Сценарий A — Worker Restart

Во время активного мониторинга:

1. Запусти тестовые мониторы.
2. Подтверди получение реальных CheckResult.
3. Перезапусти worker.
4. Проверь восстановление scheduling.
5. Проверь соблюдение lease.
6. Проверь отсутствие дублирующихся результатов.
7. Проверь отсутствие искусственных DOWN.

### Сценарий B — PostgreSQL Outage

Во время нагрузки:

1. Временно сделай тестовую PostgreSQL недоступной.
2. Убедись, что ошибки обрабатываются корректно.
3. Восстанови PostgreSQL.
4. Проверь возобновление работы.
5. Проверь целостность истории.
6. Проверь состояние инцидентов.

Не используй основную пользовательскую базу для разрушающих проверок.

### Сценарий C — Slow Targets

Создай смешанную нагрузку:

- Быстрые HTTP-запросы.
- Медленные HTTP-запросы.
- Таймауты.
- HTTP 500.
- Успешные HTTP 200.

Проверь, что медленные сайты не блокируют остальные мониторы.

### Сценарий D — Concurrent Configuration Changes

Во время активной нагрузки:

- Edit.
- Pause.
- Resume.
- Run Now.
- Delete.
- Group changes.

Проверь отсутствие повреждения данных и неправильного сохранения устаревших результатов.

### Сценарий E — SSE

Во время нагрузки открой два независимых браузерных клиента.

Проверь:

- Актуальность dashboard.
- Изменение состояний.
- Incidents.
- Reconnect.
- Отсутствие бесконечных запросов.
- Отсутствие существенной деградации API.

### Метрики

Фиксируй:

- Длительность теста.
- Количество мониторов.
- Количество проверок.
- Число ошибок.
- Число подтверждённых ожидаемых HTTP-ошибок.
- Scheduler delay.
- Concurrency.
- Recovery time.
- Время ответа API.
- CPU.
- RAM.
- PostgreSQL metrics.

Отличай ожидаемые HTTP 500 от ошибок самого ServicePulse.

Не делай ложных выводов из числа проверок без учёта fixed-delay scheduling.

## 7. BENCHMARK И АНАЛИЗ ХОЛОДНЫХ ЗАПРОСОВ

Предыдущие измерения:

- Первый запрос: 1,143 секунды.
- Наборы до 1 млн синтетических строк.

Необходимо исследовать причину более медленного первого запроса.

- SQL query plan.
- Buffers.

- Serialization.
- Connection overhead.
- Python processing.
- Cold vs warm execution.

Отдельно фиксируй:

- Cold latency.
- Warm p50.
- Warm p95.
- Warm p99.
- Maximum latency.
- Dataset size.
- Number of buckets.
- Query count.
- Response size.
- Environment.

Если есть подтверждённое узкое место, исправь его минимальными изменениями.

Не добавляй сложную инфраструктуру без необходимости.

### Acceptance

Цель — стабильное выполнение месячной агрегации в разумном временном бюджете.

Если холодный запрос иногда превышает секунду, честно зафиксируй это.

Не объявляй безусловный p95 меньше секунды, если результаты его не подтверждают.

# ЧАСТЬ IV — ПОЛНЫЙ МОНОХРОМНЫЙ РЕДИЗАЙН

## 8. ОСНОВНАЯ ЗАДАЧА

Полностью переработай существующий интерфейс ServicePulse в профессиональном **чёрно-белом минималистичном стиле**.

Это полноценная реализация дизайна, а не замена нескольких CSS-переменных.

### Главная концепция

Создай визуально цельную B2B SaaS-платформу.

Основной подход:

- Белая рабочая область.
- Чёрный или графитовый sidebar.
- Чёрная типографика.
- Белые карточки.
- Серые границы.
- Чёрные основные кнопки.
- Светлые вторичные кнопки.
- Чистые таблицы.
- Минималистичные графики.
- Контрастные статусы.
- Хорошие отступы.
- Современные формы.

Запрещено возвращать старую зелёную тему.

Избегай:

- Случайных градиентов.
- Неоновых элементов.
- Перегруженных карточек.
- Чрезмерно мелкого текста.
- Непоследовательных отступов.
- Большого количества теней.
- Избыточных анимаций.

При этом интерфейс не должен становиться безликим.

Единая типографика, сетка и аккуратные компоненты должны создавать индивидуальность ServicePulse.
