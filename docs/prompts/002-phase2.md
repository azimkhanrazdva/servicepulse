## 4. Основная задача — полное управление мониторами

После аудита существующей реализации переходи к разработке следующей функциональной части.

Необходимо реализовать полноценное управление HTTP-мониторами.

### 4.1. Создание и редактирование

Пользователь должен иметь возможность:

- Создать монитор.
- Изменить монитор.
- Удалить монитор.
- Изменить его название.
- Изменить URL.
- Установить интервал от 30 до 3600 секунд.
- Установить HTTP timeout.
- Указать ожидаемый HTTP-код.
- Указать необязательную строку, которая должна присутствовать в HTTP-ответе.

Все настройки должны храниться в PostgreSQL.

Проверяй входные данные и возвращай понятные ошибки.

### 4.2. Управление состоянием

Реализуй:

- Pause.
- Resume.
- Run Now.

Обязательные условия:

1. Приостановленный монитор не выполняет новые автоматические проверки.
2. При возобновлении расписание восстанавливается корректно.
3. Изменение интервала учитывается при последующих запусках.
4. Изменение URL применяется к последующим проверкам.
5. Удалённый монитор не продолжает выполнять новые проверки.
6. Ручная проверка не приводит к опасному параллельному выполнению той же проверки.
7. Результаты уже запущенных задач корректно обрабатываются при изменении конфигурации.
8. После перезапуска сервера настройки сохраняются.

### 4.3. Группы мониторов

Реализуй:

- Создание группы.
- Редактирование группы.
- Удаление группы.
- Добавление монитора в группу.
- Удаление монитора из группы.
- Просмотр всех мониторов группы.
- Общий статус группы.
- Настройку email-получателей для группы.

Самостоятельно разработай и документируй однозначные правила вычисления группового статуса.

Учитывай:

- Пустые группы.
- Группы с работающими мониторами.
- Группы с упавшими мониторами.
- Приостановленные мониторы.
- Мониторы без результатов проверки.

Не допускай противоречий между статусом отдельных мониторов и статусом группы.

## 7. Проверки конкурентности и согласованности

Отдельно протестируй следующие сценарии:

1. Монитор редактируется во время HTTP-проверки.
2. Пользователь удаляет монитор во время проверки.
3. Пользователь нажимает Run Now несколько раз.
4. Пользователь приостанавливает монитор во время работы worker.
5. Две вкладки одновременно редактируют настройки.
6. Изменяется интервал запланированной проверки.
7. Worker перезапускается после изменения конфигурации.
8. Пользователь одновременно изменяет группу и настройки монитора.

Не допускай молчаливой потери данных.

Выбери разумную модель защиты от конфликтов и документируй её.

Если для предотвращения гонок нужны транзакции, блокировки либо контроль версий, реализуй подходящее решение.

Не добавляй сложность без необходимости.

## 10. Git и коммиты

Перед коммитом:

1. Проверь `git status`.
2. Изучи `git diff`.
3. Убедись в отсутствии секретов.
4. Убедись, что изменены только необходимые файлы.
5. Выполни соответствующие тесты.
6. Обнови development log.
7. Создай осмысленный локальный коммит.

Используй Conventional Commits.

Например:

- `feat(api): add monitor configuration management`
- `feat(groups): implement monitor groups`
- `feat(ui): add monitor management interface`
- `test: cover monitor concurrency scenarios`

Не создавай коммиты искусственно для увеличения их количества.

Сохраняй настоящую последовательность разработки.

Если первый PR ещё не опубликован и не объединён, не начинай новую ветку от устаревшего `main` так, чтобы потерять предыдущую работу.

Перед созданием новой ветки проверь историю и зависимости между изменениями.

Публикация и merge — только после моего разрешения.
