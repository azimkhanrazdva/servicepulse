## 4. Основная функциональность — Incident Lifecycle

Разработай полноценную модель жизненного цикла инцидентов.

### 4.1. Создание инцидента

Инцидент должен открываться только после достижения настроенного порога последовательных неуспешных проверок.

Пример:

Начальное состояние: UP.

Первая ошибка:
- Увеличивается счётчик ошибок.
- Сайт пока не считается подтверждённо упавшим.
- Инцидент не создаётся.

Вторая последовательная ошибка при threshold=2:
- Состояние переходит в DOWN.
- Создаётся новый инцидент.
- Сохраняется момент подтверждения падения.
- Инцидент получает статус OPEN.
- Данные становятся доступны через API и SSE.

Последующие ошибки:
- Состояние остаётся DOWN.
- Не создаётся второй инцидент.
- Существующий инцидент остаётся открытым.
- Продолжительность падения увеличивается.

### 4.2. Восстановление

Когда монитор находится в DOWN и следующая проверка завершается успешно:

1. Состояние меняется на UP.
2. Открытый инцидент закрывается.
3. Сохраняется время восстановления.
4. Вычисляется длительность инцидента.
5. История остаётся доступной.
6. Интерфейс получает обновлённые данные.

Не создавай дополнительные инциденты при повторных успешных запросах.

### 4.3. Правила времени

Все события сохраняй с корректными UTC timestamps.

Определи:

- opened_at — момент подтверждённого падения.
- recovered_at — момент подтверждённого восстановления.
- duration — разница между ними.
- Для открытого инцидента — продолжительность до текущего времени.

Не используй время первого неуспешного запроса как подтверждённое начало инцидента без явного архитектурного решения.

Сохраняй различие между временем HTTP-наблюдения и временем обработки.

Для тестов используй контролируемые часы там, где это позволяет архитектура.

## 5. PostgreSQL — постоянное хранение инцидентов

Создай следующую аддитивную миграцию Alembic после существующей 0002.

Предпочтительно:

0003_incidents.py

Миграция должна быть совместима с уже существующими данными.

### 5.1. Incident Model

Предлагаемая структура:

- id — UUID.
- monitor_id — UUID / Foreign Key.
- opened_at — TIMESTAMPTZ.
- recovered_at — nullable TIMESTAMPTZ.
- closure_reason — nullable.
- created_at — TIMESTAMPTZ.
- updated_at — TIMESTAMPTZ при необходимости.

Оцени, нужны ли дополнительные поля.

Не дублируй сущности без необходимости.

### 5.2. Ограничения целостности

Обязательно обеспечь:

- Не более одного открытого инцидента на один монитор.
- Корректную связь incident → monitor.
- Невозможность времени восстановления раньше времени начала.
- Корректное поведение при удалении монитора.
- Уникальность открытого инцидента даже при конкурентных транзакциях.

Рассмотри частичный уникальный индекс PostgreSQL для открытых инцидентов:

UNIQUE monitor_id WHERE recovered_at IS NULL

Если выбранная модель требует другой структуры, объясни причину.

Не используй только Python-проверку наличия открытого инцидента без гарантий на уровне PostgreSQL.

### 5.3. Миграция существующих данных

Особенно внимательно обработай уже существующие мониторы в состоянии DOWN.

На момент миграции у них могут быть неуспешные проверки, но ещё не существовать записи Incident.

Разработай явную политику перехода:

- Не создавать вымышленных исторических событий.
- Не терять реальное текущее состояние.
- Не создавать дубли при следующей ошибке.
- Не объявлять сайт восстановленным без успешного запроса.
- Объяснить ограничения восстановления старой истории.

Сохрани существующие HTTP observations и настройки мониторов.

Напиши миграционный интеграционный тест на базе с данными этапа 2.

## 6. Конкурентность и атомарные транзакции

Это один из важнейших критериев качества.

Состояние monitor, счётчик ошибок, новый HTTP CheckResult и запись Incident должны изменяться согласованно.

При необходимости объедини их в одну транзакцию PostgreSQL.

### Обязательные гарантии

1. Два worker не открывают два одинаковых инцидента.
2. Повторное выполнение задачи не создаёт повторный инцидент.
3. Устаревшая проверка не изменяет текущий incident.
4. Изменение версии конфигурации корректно отменяет устаревший результат.
5. Потеря соединения с PostgreSQL не оставляет частично записанный переход состояния.
6. Конкурентные результаты не нарушают порядок обработки.
7. Перезапуск worker не открывает второй инцидент для уже существующего падения.
8. Неуспешная транзакция не оставляет monitor DOWN без необходимой согласованной записи, если данный переход должен открыть инцидент.

Сохраняй существующие lease tokens и механизм проверки config_version.

Используй уже принятые архитектурные решения.

Не вводи Redis или распределённые очереди, если в них нет обоснованной необходимости.

## 7. Pause, Resume, Edit и Delete при открытом инциденте

Это критически важная часть, которую легко реализовать неправильно.

Продумай поведение для следующих операций.

### PAUSE во время DOWN

Если пользователь приостанавливает монитор с активным инцидентом:

- Не объявляй сайт восстановленным без успешной проверки.
- Не создавай ложный recovery.
- Не оставляй историю в противоречивом состоянии.

Предлагаемое решение: административное закрытие инцидента с причиной PAUSED, отличной от подтверждённого восстановления.

Оцени этот вариант и зафиксируй решение.

### RESUME

При возобновлении:

- Монитор возвращается к проверкам.
- Состояние определяется согласно существующей политике UNKNOWN.
- Счётчик ошибок начинается заново.
- Новый инцидент создаётся только после достижения порога.

### EDIT во время DOWN

Текущая архитектура сбрасывает состояние и счётчик ошибок при изменении конфигурации.

Необходимо согласовать это с Incident Model.

Предлагаемый вариант: завершать старый инцидент с причиной CONFIG_CHANGED без генерации ложного события восстановления.

Новое падение должно определяться по актуальной конфигурации.

Учитывай, что даже изменение названия сейчас приводит к сбросу состояния — проверь этот компромисс и задокументируй его.

### DELETE

При удалении монитора:

- Не остаётся открытого инцидента без корректного владельца.
- Отложенные результаты не могут восстановить удалённый монитор.
- Каскадное удаление или сохранение аудиторской истории является явным архитектурным решением.

Не меняй поведение удаления из этапа 2 без обоснования.

### Главное правило

**Административное завершение мониторинга не равно подтверждённому восстановлению доступности сайта.**

Модель данных, API и будущие email-уведомления должны уметь различать эти события.

## 10. Надёжность scheduler и worker

Удели внимание текущим ограничениям, описанным в docs/architecture.md.

Сейчас используются leases с ограниченным временем жизни. Это защищает систему от многих гонок, но не является абсолютной гарантией отсутствия двух одновременно выполняющихся HTTP-запросов при произвольной длительной остановке процесса.

Не заявляй более сильных гарантий, чем реально обеспечивает механизм.

Проверь следующие сценарии:

1. Медленная HTTP-проверка.
2. Проверка превышает свой интервал.
3. Перезапуск worker во время запроса.
4. Потеря worker после получения lease.
5. Истечение lease.
6. Возврат старой задачи после истечения lease.
7. Два worker пытаются получить одну задачу.
8. Ошибка PostgreSQL во время сохранения результата.
9. Изменение монитора при активном запросе.
10. Отмена задачи при остановке контейнера.

Требования:

- Никаких вымышленных результатов.
- Никаких ложных падений во время простоя worker.
- Никаких повторных открытых инцидентов.
- Никаких несогласованных переходов.
- Существующий механизм параллельных проверок не должен деградировать.

При необходимости внеси минимальные исправления в worker.

Каждое исправление должно иметь воспроизводимый тест.
